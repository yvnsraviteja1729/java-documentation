## 1. What is GraphQL?
**GraphQL** is a **query language for APIs** and a **runtime** for executing those queries against your data. It was developed at Facebook in 2012, open-sourced in 2015, and is now governed by the GraphQL Foundation.

### The One-Liner Definition
>  _GraphQL is a typed, schema-first API specification that lets clients request exactly the data they need — no more, no less — through a single endpoint._ 

### Key Properties
- **Single endpoint** (typically `/graphql` ) — not multiple URLs.
- **Client-specified queries** — the client declares what data it wants.
- **Strongly typed schema** — every field has a type, validated at runtime.
- **Hierarchical** — queries mirror the shape of the response.
- **Transport-agnostic** — usually over HTTP POST, but works over WebSocket, gRPC, etc.
```graphql
query {
  user(id: "123") {
    name
    email
    orders(last: 3) {
      id
      total
      items { product { name } }
    }
  }
}
```
The response shape **exactly matches** the query shape:

```json
{
  "data": {
    "user": {
      "name": "Alice",
      "email": "alice@example.com",
      "orders": [
        { "id": "1", "total": 99.99, "items": [...] }
      ]
    }
  }
}
```

## 2. Why GraphQL Exists — Problems It Solves
### 2.1 The REST Pain Points
| Problem | REST Behavior | GraphQL Solution |
| ----- | ----- | ----- |
| **Over-fetching** | Endpoint returns full user object even if you only need the name | Client requests only `name`  |
| **Under-fetching** | Need to call `/users/1`, then `/users/1/orders`, then `/orders/X/items`  | One query returns everything nested |
| **Versioning** | Endpoints versioned (`/v1`, `/v2`) | Fields are deprecated; no versions |
| **Multiple round trips** | N requests for related data | One request, server resolves the graph |
| **Tight coupling to UI** | Endpoint shape rarely matches UI needs | Client shapes the response |
| **Documentation drift** | Swagger/OpenAPI optional and often outdated | Schema is mandatory and introspectable |
### 2.2 The Mobile Driver
Facebook built GraphQL for its mobile apps. On slow 3G networks, REST's over-fetching killed performance. GraphQL was designed so a mobile client could fetch the entire screen's data in **one network round trip with minimal payload**.

### 2.3 The Microservices Aggregation Problem
In a microservices world, a single UI screen needs data from many services. Without GraphQL, you'd typically build a **BFF (Backend-for-Frontend)** that aggregates manually. GraphQL automates this aggregation declaratively.

## 3. Core Concepts
GraphQL is built on five foundational ideas:

### 3.1 Schema
The contract between client and server — defines all available types, fields, queries, mutations, and subscriptions. Written in **SDL (Schema Definition Language)**.

### 3.2 Type System
Strongly typed. Every field has a declared type. Type-checked at query time.

### 3.3 Operations
Three operation types:

- **Query** — read.
- **Mutation** — write.
- **Subscription** — real-time push.
### 3.4 Resolvers
Server-side functions that fetch the actual data for each field.

### 3.5 Introspection
Clients can ask the server _"what queries do you support, what types do you have?"_ — enables tools like GraphiQL, Apollo Studio, and codegen.

## 4. Schema Definition Language (SDL)
The schema is the heart of GraphQL. It's the **source of truth** — the API contract.

```graphql
type User {
  id: ID!
  name: String!
  email: String
  orders: [Order!]!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

type OrderItem {
  product: Product!
  quantity: Int!
}

type Product {
  id: ID!
  name: String!
  price: Float!
}

enum OrderStatus {
  PENDING
  SHIPPED
  DELIVERED
  CANCELLED
}

type Query {
  user(id: ID!): User
  users(limit: Int = 10): [User!]!
  order(id: ID!): Order
}

type Mutation {
  createOrder(input: CreateOrderInput!): Order!
  cancelOrder(id: ID!): Order!
}

type Subscription {
  orderUpdated(userId: ID!): Order!
}

input CreateOrderInput {
  userId: ID!
  items: [OrderItemInput!]!
}

input OrderItemInput {
  productId: ID!
  quantity: Int!
}
```
### Notation
- `!`  after a type = **non-null** (required).
- `[Type!]!`  = a non-null array of non-null items.
- `input`  types are for arguments (cannot be returned).
- `enum`  for fixed sets of values.

## 5. Types in GraphQL
### 5.1 Scalar Types (Built-in)
| Scalar | Description |
| ----- | ----- |
| `Int`  | 32-bit signed integer |
| `Float`  | Double-precision floating point |
| `String`  | UTF-8 string |
| `Boolean`  | true/false |
| `ID`  | Unique identifier (serialized as string) |
You can also define **custom scalars**: `DateTime`, `Email`, `URL`, `UUID`, `JSON`, etc.

### 5.2 Object Types
Composite types with fields (most common):

```graphql
type User {
  id: ID!
  name: String!
}
```
### 5.3 Input Types
Used **only** as arguments to mutations/queries. Cannot be returned.

```graphql
input UserInput {
  name: String!
  email: String!
}
```
### 5.4 Enums
Fixed set of values:

```graphql
enum Role {
  ADMIN
  USER
  GUEST
}
```
### 5.5 Interfaces
Abstract type other types can implement (polymorphism):

```graphql
interface Node {
  id: ID!
}

type User implements Node {
  id: ID!
  name: String!
}

type Order implements Node {
  id: ID!
  total: Float!
}
```
### 5.6 Unions
A field can return one of several types:

```graphql
union SearchResult = User | Order | Product

type Query {
  search(q: String!): [SearchResult!]!
}
```
Queries use **inline fragments**:

```graphql
query {
  search(q: "ali") {
    ... on User { name }
    ... on Order { total }
    ... on Product { price }
  }
}
```
### 5.7 Lists & Non-Null
```graphql
[String]      # nullable list of nullable strings
[String!]     # nullable list of non-null strings
[String]!     # non-null list of nullable strings
[String!]!    # non-null list of non-null strings (most common)
```

## 6. Queries
Queries read data — analogous to REST `GET`.

### 6.1 Basic Query
```graphql
query {
  user(id: "1") {
    name
    email
  }
}
```
### 6.2 Multiple Fields
```graphql
query {
  me { name }
  popularProducts { id name price }
}
```
### 6.3 Nested Queries
```graphql
query {
  user(id: "1") {
    name
    orders {
      id
      items {
        product {
          name
        }
      }
    }
  }
}
```
This is the killer feature: deep, related data in **one request**.

### 6.4 Arguments
Arguments can be passed at any level:

```graphql
query {
  user(id: "1") {
    orders(last: 5, status: SHIPPED) {
      id
    }
  }
}
```

## 7. Mutations
Mutations change data — analogous to REST `POST/PUT/DELETE`.

```graphql
mutation {
  createOrder(input: {
    userId: "1"
    items: [
      { productId: "p1", quantity: 2 }
    ]
  }) {
    id
    total
    status
  }
}
```
### Key Differences from Queries
- **Sequential** — mutations at the top level execute in order; query fields execute in parallel.
- Convention: mutations should return the modified object (lets the client refresh state in one call).
- Often paired with **input types**.
---

## 8. Subscriptions
Subscriptions push **real-time updates** from server to client, typically over WebSocket.

```graphql
subscription {
  orderUpdated(userId: "1") {
    id
    status
  }
}
```
The server sends a new event each time the subscription condition triggers.

### Use Cases
- Live chat, notifications.
- Order status updates.
- Dashboards (stock, sports scores).
- Collaboration apps (Figma, Google Docs-style).
### Implementation Notes
- Transport: WebSocket (`graphql-ws`  protocol).
- Server keeps state per connection (so subscriptions are **stateful**).
- Requires a **pub/sub backplane** (Redis, Kafka) to scale across instances.

## 9. Resolvers
A **resolver** is a function that returns the data for a field. The runtime walks the query tree and calls a resolver for each field.

### 9.1 Resolver Anatomy
Every resolver receives **4 arguments**:

```js
fieldResolver(parent, args, context, info)
```
| Arg | Description |
| ----- | ----- |
| `parent`  | The object returned from the parent field |
| `args`  | Arguments passed to this field |
| `context`  | Shared per-request context (auth, dataloaders, DB connection) |
| `info`  | Execution info (current path, schema, etc.) |
### 9.2 Example Resolvers (JavaScript/Apollo)
```js
const resolvers = {
  Query: {
    user: (_, { id }, { db }) => db.users.findById(id),
    users: (_, { limit }, { db }) => db.users.findAll(limit),
  },

  User: {
    // resolves the orders field for any User
    orders: (user, _, { db }) => db.orders.findByUserId(user.id),
  },

  Order: {
    items: (order, _, { db }) => db.items.findByOrderId(order.id),
  },

  Mutation: {
    createOrder: (_, { input }, { db, user }) => {
      authorize(user);
      return db.orders.create({ ...input, userId: user.id });
    },
  },
};
```
### 9.3 Default Resolvers
If you don't supply a resolver, GraphQL automatically reads `parent[fieldName]`. So `User.name` doesn't need an explicit resolver if `parent.name` exists.

### 9.4 Where Resolvers Get Their Data
Resolvers can fetch from:

- Databases (SQL, NoSQL).
- Internal microservices (REST, gRPC).
- External APIs (Stripe, Twilio).
- Cache (Redis).
- File system / S3.
This is why GraphQL works beautifully as an **aggregation layer over microservices**.

## 10. Fragments, Variables, Aliases, Directives
### 10.1 Variables
Avoid string concatenation; pass arguments as variables.

```graphql
query GetUser($id: ID!) {
  user(id: $id) { name email }
}
```
```json
{ "id": "1" }
```
### 10.2 Fragments
Reusable selection sets — DRY.

```graphql
fragment UserBasics on User {
  id
  name
  email
}

query {
  me { ...UserBasics }
  user(id: "2") { ...UserBasics }
}
```
### 10.3 Aliases
Rename a field in the response:

```graphql
query {
  alice: user(id: "1") { name }
  bob:   user(id: "2") { name }
}
```
Useful when querying the same field with different arguments.

### 10.4 Directives
Conditional inclusion in the query:

```graphql
query GetUser($withOrders: Boolean!) {
  user(id: "1") {
    name
    orders @include(if: $withOrders) { id }
  }
}
```
Built-in directives: `@include`, `@skip`, `@deprecated`.

Custom directives are common: `@auth`, `@rateLimit`, `@cache`, `@cost`.

## 11. Introspection
GraphQL servers expose their schema through standard queries:

```graphql
query {
  __schema {
    types { name }
  }
  __type(name: "User") {
    fields { name type { name } }
  }
}
```
This enables:

- **GraphiQL / Apollo Sandbox** — interactive query explorers.
- **Code generation** — typed clients (`graphql-codegen` ).
- **Documentation** — auto-generated.
- **Tooling** — linters, mocks, contract tests.
>  ⚠️ **In production, disable introspection on public endpoints** — it gives attackers your full schema.

## 12. The N+1 Problem & DataLoader
### 12.1 The Problem
```graphql
query {
  users {       # 1 DB query → returns 100 users
    name
    orders {    # 100 more queries (one per user) — N+1!
      id
    }
  }
}
```
Naive resolvers fire **101 database queries** for what should be 2.

### 12.2 The Solution: Batching with DataLoader
Facebook's **DataLoader** library (and equivalents in every language) **batches and caches** field requests within a single request.

```js
const orderLoader = new DataLoader(async (userIds) => {
  const orders = await db.orders.findByUserIds(userIds);  // 1 query
  return userIds.map(id => orders.filter(o => o.userId === id));
});
```
Now the resolver uses the loader:

```js
User: {
  orders: (user, _, { orderLoader }) => orderLoader.load(user.id),
}
```
DataLoader collects all `.load(id)` calls within the same event loop tick, fires **one batched query**, and returns the results in order.

### 12.3 Performance Impact
The same query goes from 101 DB calls to **2** — often a 50–100× speedup.

>  The N+1 problem is the single most important production concern in GraphQL. Senior interviewers will ask about it.

## 13. Error Handling
GraphQL has a unique error model: a response **can contain both **`**data**`** and **`**errors**` simultaneously.

```json
{
  "data": {
    "user": { "name": "Alice", "orders": null }
  },
  "errors": [
    {
      "message": "Failed to fetch orders",
      "path": ["user", "orders"],
      "extensions": { "code": "DOWNSTREAM_FAILURE" }
    }
  ]
}
```
### Patterns
- **Partial success** — return what you can; mark the failed field null.
- **Error extensions** — standardized in Apollo: `extensions.code`  for clients to handle.
- **Typed errors** in the schema (union types):
```graphql
union LoginResult = LoginSuccess | LoginFailure

type LoginSuccess { token: String! }
type LoginFailure { reason: String! }
```
>  Best practice in modern GraphQL: model **business errors as types**, not as runtime errors.

## 14. Caching in GraphQL
GraphQL caching is **harder** than REST because:

- Single endpoint (`/graphql` ) → no URL-based caching.
- Mostly POST requests → not cacheable by default.
- Queries can be infinitely varied.
### 14.1 Server-Side Caching
- **Cache resolvers** — cache the underlying data source (Redis, in-memory).
- **Persisted queries** — server stores known query → hash; client sends only the hash; queries become cacheable by hash.
- **Automatic Persisted Queries (APQ)** — Apollo standard.
### 14.2 Client-Side Caching
- **Apollo Client** and **Relay** maintain a **normalized cache** in memory.
- Objects identified by `__typename + id`  are stored once and referenced.
- Mutations update the cache automatically.
### 14.3 CDN Caching
With persisted queries, you can use `GET` requests with cacheable URLs → CDN-friendly.

## 15. Pagination
GraphQL doesn't dictate a pagination style, but two are standard:

### 15.1 Offset-based (Simple but Limited)
```graphql
type Query {
  users(offset: Int = 0, limit: Int = 10): [User!]!
}
```
Easy but doesn't scale, jumps when data changes.

### 15.2 Cursor-based (Relay Connection Spec)
```graphql
type UserConnection {
  edges: [UserEdge!]!
  pageInfo: PageInfo!
}

type UserEdge {
  cursor: String!
  node: User!
}

type PageInfo {
  hasNextPage: Boolean!
  endCursor: String
}
```
Query:

```graphql
query {
  users(first: 10, after: "cursor-xyz") {
    edges {
      cursor
      node { name }
    }
    pageInfo { hasNextPage endCursor }
  }
}
```
>  This is the **standard for production GraphQL APIs** (GitHub, Shopify, all use cursors).

## 16. Authentication & Authorization
### 16.1 Authentication
- Auth typically happens **before** GraphQL — in middleware that extracts a JWT/session.
- The authenticated user is placed in `context` .
- Resolvers read `context.user` .
```js
app.use('/graphql', authMiddleware, graphqlHandler);
```
### 16.2 Authorization
Two main approaches:

#### a) In Resolvers
```js
User: {
  email: (parent, _, ctx) => {
    if (ctx.user.id !== parent.id && !ctx.user.isAdmin) return null;
    return parent.email;
  },
}
```
#### b) Via Directives
```graphql
type User {
  email: String @auth(requires: SELF_OR_ADMIN)
}
```
The directive runs before the resolver and rejects unauthorized access.

### 16.3 Field-Level Security
GraphQL exposes data **at the field level**, so authorization must also be enforced field by field — not just per endpoint.

## 17. Security Concerns
GraphQL's flexibility is also its biggest risk.

### 17.1 Query Depth Attacks
```graphql
query {
  user { friends { friends { friends { friends { ... } } } } }
}
```
Mitigate with **depth limits** (`graphql-depth-limit`).

### 17.2 Query Complexity Attacks
A shallow but expensive query can DoS the server.

Mitigate with **query cost analysis** (`graphql-cost-analysis`) — assign cost per field and reject queries above a threshold.

### 17.3 Introspection
Disable in production for public APIs.

### 17.4 Aliases Abuse
```graphql
{
  a1: expensiveField
  a2: expensiveField
  a3: expensiveField
  ...
}
```
Mitigate with **rate limiting** + complexity analysis.

### 17.5 Batching Attacks
Some clients batch many queries in one HTTP request — rate-limit operations, not requests.

### 17.6 Recommended Defenses
| Defense | Tool |
| ----- | ----- |
| Depth limit | `graphql-depth-limit`  |
| Complexity limit | `graphql-cost-analysis`  |
| Persisted queries | Apollo, Relay |
| Rate limit | API gateway / WAF |
| Timeouts | Per resolver |
| Disable introspection | Server config |
| Auth on every field | Directives or middleware |

## 18. GraphQL vs REST vs gRPC
| Aspect | REST | gRPC | GraphQL |
| ----- | ----- | ----- | ----- |
| **Style** | Resource-oriented | RPC | Query language |
| **Transport** | HTTP/1.1, HTTP/2 | HTTP/2 | HTTP (POST), WebSocket |
| **Schema** | Optional (OpenAPI) | Required (.proto) | Required (SDL) |
| **Format** | JSON | Protobuf (binary) | JSON |
| **Endpoints** | Many | Many (services × methods) | One |
| **Over/under-fetching** | Common | Same | Solved |
| **Streaming** | SSE / chunked | Native (4 modes) | Subscriptions |
| **Caching** | Excellent (HTTP) | Hard | Hard (needs persisted queries) |
| **Browser** | Native | Needs gRPC-Web | Native |
| **Best for** | Public APIs, CRUD | Internal microservices | UI aggregation, mobile |
### When to Pick GraphQL
✅ Mobile or web UI with many related entities.
✅ Aggregating multiple microservices for the client.
✅ Public APIs where consumers have varied data needs (GitHub).
✅ Rapidly evolving frontends.

### When NOT to Pick GraphQL
❌ Internal service-to-service RPC (use gRPC).
❌ Simple CRUD with few clients (REST is simpler).
❌ Heavy file uploads (REST + S3 better).
❌ Caching is mission-critical and you can't manage persisted queries.

## 19. GraphQL Federation
A single GraphQL service that owns all schema = a new monolith. **Federation** solves this.

### 19.1 What It Is
**Apollo Federation** lets multiple GraphQL services (subgraphs) compose into one **supergraph**, presented as a single endpoint by a **gateway**.

```
┌─────────────────────┐
  Client ──► │  GraphQL Gateway    │
             └──────┬──────┬───────┘
                    │      │
      ┌─────────────┘      └────────────┐
      ▼                                  ▼
┌────────────┐                  ┌────────────┐
│ Users SG   │                  │ Orders SG  │
│ (subgraph) │                  │            │
└────────────┘                  └────────────┘
```
### 19.2 Entities & References
Each subgraph owns entities and can **extend** entities owned by others.

```graphql
# Users subgraph
type User @key(fields: "id") {
  id: ID!
  name: String!
}

# Orders subgraph
extend type User @key(fields: "id") {
  id: ID! @external
  orders: [Order!]!
}
```
The gateway plans the query: fetch from Users SG, then enrich with Orders SG.

### 19.3 Why Federation Matters
- Each team owns its subgraph.
- No central GraphQL team becomes a bottleneck.
- Independent deploys.
- Used at Apollo, Netflix, Expedia, PayPal.

## 20. GraphQL in Microservices
### 20.1 Common Architectures
#### a) Single Gateway BFF
One GraphQL server fans out to many REST/gRPC services.

```
Client → GraphQL Server → REST/gRPC microservices
```
Simple. Best for small-to-medium teams.

#### b) Federated Supergraph
Each microservice exposes its own subgraph; a gateway composes them.

Best for large orgs where teams want autonomy.

#### c) GraphQL on the Edge
GraphQL becomes the **public API** layer; internal services use gRPC.

This is the **Netflix model**.

### 20.2 Trade-offs
| Pro | Con |
| ----- | ----- |
| Massively reduces over/under-fetching | Adds a new layer to operate |
| One contract for all clients | Resolver fan-out can DDOS downstream |
| Strong types end-to-end | N+1 traps |
| Excellent for mobile | Complex caching story |

## 21. Best Practices
✅ **Do:**

- Treat the schema as a contract — review changes carefully.
- Use **input types** for mutation arguments.
- Use **DataLoader** for every list resolver that hits a backend.
- Make mutations **return the full updated object**.
- Use **cursor-based pagination** (Relay-style).
- Enforce **field-level authorization**.
- Use **persisted queries** in production for security and caching.
- Disable introspection on public endpoints.
- Set **query depth and cost limits**.
- Log slow resolvers — instrument with tracing (Apollo Studio, OpenTelemetry).
❌ **Don't:**

- Expose internal DB schema 1:1 — design the schema for the **client**.
- Mix mutation + side-effect logic in resolvers (use a service layer).
- Forget timeouts on downstream calls.
- Allow arbitrary depth/breadth.
- Add a "god type" with hundreds of fields.
- Roll your own auth in every resolver — use directives or middleware.

## 23. Common Pitfalls
| Pitfall | Symptom | Fix |
| ----- | ----- | ----- |
| N+1 queries | Slow responses; DB CPU spike | DataLoader |
| Unbounded queries | One client DoSes the server | Depth + cost limits |
| Schema becomes a god graph | Endless coordination | Federation |
| Resolvers do too much | Hard to test | Push logic to services |
| Hidden authorization gaps | Field-level data leaks | Directive-based authz |
| Cache invalidation pain | Stale UI | Normalized client caches (Apollo) |
| Breaking changes | Clients break silently | `@deprecated` + schema CI checks |
| Subscriptions don't scale | One instance handles all WS | Redis/Kafka backplane |

```
Schema (the contract)
                       │
     ┌─────────────────┼─────────────────┐
     ▼                 ▼                 ▼
  Queries          Mutations         Subscriptions
     │                 │                 │
     ▼                 ▼                 ▼
```
