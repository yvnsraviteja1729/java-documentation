# Part 1: What Is Kafka?
Apache Kafka is a **distributed, partitioned, replicated, append-only commit log** that doubles as a messaging system, a streaming platform, and a storage layer.

Originally built at LinkedIn (2010) to solve the problem of moving hundreds of GB/sec of activity data between systems, it has become the de-facto backbone for event-driven architectures.

**Three core capabilities:**

1. **Publish/Subscribe** to streams of records (like a message queue).
2. **Store** streams durably and reliably (like a database / log).
3. **Process** streams in real time (via Kafka Streams / ksqlDB).

# Part 2: Core Concepts
## 2.1 Topic
A **named stream of records** — e.g., `orders`, `payments`, `user-clicks`. Topics are append-only logs.

## 2.2 Partition
Each topic is split into **partitions**, which are the unit of parallelism, ordering, and storage.

```
Topic: "orders"
┌─────────────────────────────────────────────────┐
│ Partition 0:  [m0][m1][m2][m3][m4][m5]...       │  → ordered log
│ Partition 1:  [m0][m1][m2][m3]...               │
│ Partition 2:  [m0][m1][m2][m3][m4]...           │
└─────────────────────────────────────────────────┘
```
- Ordering is **only guaranteed within a partition**, never across them.
- Each record has an **offset** — its position within the partition (0, 1, 2, …).
- Partitions are distributed across brokers in the cluster.
## 2.3 Broker
A Kafka server. A **cluster** is multiple brokers. Each broker hosts a subset of partitions.

## 2.4 Producer
Client that **publishes** records to topics. Decides which partition each record goes to (via key hashing, round-robin, or custom partitioner).

## 2.5 Consumer
Client that **reads** records from topics by polling. Tracks its position via **offsets**.

## 2.6 Consumer Group
A set of consumers sharing a `group.id`. Kafka **distributes partitions among consumers in the same group** — each partition is consumed by exactly one consumer in the group.

```
Topic "orders" (6 partitions)
Consumer Group "billing":
   Consumer A → partitions 0, 1
   Consumer B → partitions 2, 3
   Consumer C → partitions 4, 5
```
Add a 4th consumer → rebalance, each gets fewer partitions.
Add a 7th consumer → it sits idle (parallelism is bounded by partition count).

## 2.7 Replication
Each partition has **N replicas**: 1 **leader** + N-1 **followers**. All reads/writes go through the leader; followers replicate asynchronously. If the leader dies, a follower from the **ISR (In-Sync Replicas)** is promoted.

## 2.8 Offset Commit
Consumers **commit offsets** to mark "I've processed up to here." Stored in the internal topic `__consumer_offsets`. On restart, consumers resume from the last committed offset.

## 2.9 Controller
One broker is elected **controller**. It manages partition leader assignments, broker membership, and metadata. In modern Kafka (KRaft mode, 2.8+) this runs on a quorum of controllers instead of ZooKeeper.

# Part 3: Internal Architecture
## 3.1 Cluster Topology
```
┌───────────────────────────────────────────────┐
│              Kafka Cluster                    │
│                                               │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐  │
│  │ Broker 1 │   │ Broker 2 │   │ Broker 3 │  │
│  │          │   │          │   │          │  │
│  │ P0 (L)   │   │ P0 (F)   │   │ P0 (F)   │  │
│  │ P1 (F)   │   │ P1 (L)   │   │ P1 (F)   │  │
│  │ P2 (F)   │   │ P2 (F)   │   │ P2 (L)   │  │
│  └──────────┘   └──────────┘   └──────────┘  │
│                                               │
│   Controller (KRaft) — metadata quorum        │
└───────────────────────────────────────────────┘
      ▲                                ▲
      │                                │
Producers                         Consumers
                              (in consumer groups)
```
L = Leader, F = Follower

## 3.2 Storage Layout — The Log on Disk
Each partition is a directory on disk containing **segment files**:

```
/var/kafka-logs/orders-0/
00000000000000000000.log      ← segment file (actual records)
00000000000000000000.index    ← offset → file position
00000000000000000000.timeindex← timestamp → offset
00000000000000012345.log      ← next segment, starts at offset 12345
00000000000000012345.index
...
```
- A partition is **a sequence of segment files**.
- New records are **appended to the active segment** (sequential write — extremely fast).
- When the segment reaches `segment.bytes`  (default 1 GB) or `segment.ms` , it's closed and a new one starts.
- Old segments are deleted (retention) or compacted (log compaction).
### Why this is so fast
- **Sequential disk I/O** — appending to a file is nearly as fast as memory on modern SSDs.
- **OS page cache** — Kafka reads/writes via `mmap`  and the kernel page cache; recent data is served from RAM with no JVM heap overhead.
- **Zero-copy** with `sendfile()`  — data goes directly from page cache → network socket, skipping user space.
- **Batching** — both producers and consumers send/receive batches of records.
- **Compression** — batches compressed end-to-end (snappy, lz4, zstd).
## 3.3 The Write Path (Producer → Broker)
1. Producer serializes the record (key + value via configured serializers).
2. **Partitioner** picks a partition:
    - If key is `null`  → sticky/round-robin.
    - Else → `hash(key) % num_partitions`  (same key → same partition → ordering preserved).

3. Record is added to an **in-memory batch buffer** keyed by `(topic, partition)` .
4. When batch is full (`batch.size` ) or `linger.ms`  elapses, the **Sender thread** flushes batches to the leader broker.
5. Leader broker appends the batch to the active segment and updates the index.
6. Followers replicate (fetch from leader).
7. Once `acks`  requirement is satisfied, leader acks the producer.
### `acks` setting
- `acks=0`  — fire and forget. Fastest, can lose data.
- `acks=1`  — leader ack only. Can lose data if leader dies before replication.
- `acks=all`  (or `-1` ) — leader waits for all ISR replicas. Strongest durability.
## 3.4 The Read Path (Consumer → Broker)
1. Consumer joins a group; the **group coordinator** (a broker) assigns partitions via a rebalance protocol.
2. Consumer calls `poll(timeout)` :
    - Sends `Fetch`  request to each partition's leader with the current offset.
    - Broker uses the offset index to find the file position, then `**sendfile()**` **s a batch** directly to the network.

3. Consumer processes records.
4. Consumer **commits offsets** (auto or manual) to `__consumer_offsets` .
### Long polling
If no data is available, the broker holds the fetch request up to `fetch.max.wait.ms` (default 500 ms) — minimizes idle CPU while keeping latency low.

## 3.5 Replication & High Availability
- Each partition has a **replication factor** (RF). RF=3 is standard for production.
- Followers continuously fetch from the leader (just like consumers do).
- A replica is in the **ISR** (In-Sync Replicas) if it's caught up within `replica.lag.time.max.ms` .
- On leader failure, the controller elects a new leader **from the ISR**.
- `min.insync.replicas`  — minimum ISR size for a write to succeed with `acks=all` . RF=3 + `min.insync.replicas=2`  is the standard durability sweet spot.
## 3.6 Retention & Log Compaction
Two retention policies:

### Time/Size-based deletion (`cleanup.policy=delete`, default)
Delete records older than `retention.ms` (default 7 days) or beyond `retention.bytes`.

### Log Compaction (`cleanup.policy=compact`)
Keep **only the latest value per key** — old values are eventually garbage-collected.
This makes the topic a "changelog" — a key/value snapshot that's eventually consistent with current state. Used by `__consumer_offsets`, Kafka Streams state stores, and **event sourcing snapshots**.

## 3.7 Rebalancing
When consumers join/leave a group or partitions change:

1. Coordinator triggers a rebalance.
2. All consumers stop, propose assignments, receive new ones, resume.
3. Modern Kafka uses **cooperative incremental rebalancing** to avoid "stop the world" pauses.

# Part 4: Java Examples
## 4.1 Producer
```java
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.StringSerializer;

import java.util.Properties;

public class OrderProducer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());

        // Durability + performance tuning
        props.put(ProducerConfig.ACKS_CONFIG, "all");                 // wait for all ISR
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);    // no duplicates on retries
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
        props.put(ProducerConfig.LINGER_MS_CONFIG, 10);               // wait 10ms to batch
        props.put(ProducerConfig.BATCH_SIZE_CONFIG, 32 * 1024);       // 32KB batches
        props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");

        try (KafkaProducer<String, String> producer = new KafkaProducer<>(props)) {
            for (int i = 0; i < 100; i++) {
                String customerId = "customer-" + (i % 10);   // key drives partition
                String payload   = "{\"orderId\":" + i + ",\"amount\":99.50}";

                ProducerRecord<String, String> record =
                        new ProducerRecord<>("orders", customerId, payload);

                producer.send(record, (RecordMetadata md, Exception ex) -> {
                    if (ex != null) ex.printStackTrace();
                    else System.out.printf("Sent to %s-%d @offset %d%n",
                            md.topic(), md.partition(), md.offset());
                });
            }
            producer.flush();   // ensure all batches are sent before close
        }
    }
}
```
**Key points:**

- The **key** (`customerId` ) ensures all orders for a customer land in the same partition → ordering per customer.
- `enable.idempotence=true`  + `acks=all`  gives **exactly-once producer semantics**.
- `linger.ms`  + `batch.size`  trade a tiny bit of latency for big throughput gains.
## 4.2 Consumer
```java
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.serialization.StringDeserializer;

import java.time.Duration;
import java.util.Collections;
import java.util.Properties;

public class OrderConsumer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "billing-service");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);   // manual commit
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 500);

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
            consumer.subscribe(Collections.singletonList("orders"));

            while (true) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
                for (ConsumerRecord<String, String> r : records) {
                    try {
                        processOrder(r.key(), r.value());     // your business logic
                    } catch (Exception e) {
                        // Send to DLQ, alert, etc. — do NOT commit
                        System.err.println("Failed: " + e.getMessage());
                    }
                }
                // commit only after successful processing of the batch
                consumer.commitSync();
            }
        }
    }

    private static void processOrder(String key, String value) {
        // idempotent: e.g., upsert by orderId
        System.out.printf("Processing %s -> %s%n", key, value);
    }
}
```
**Key points:**

- **Manual commits** after processing → at-least-once delivery (combine with idempotent `processOrder`  for effectively-once).
- `max.poll.records`  controls batch size.
- All consumers with `group.id = "billing-service"`  share partitions; a separate `group.id = "analytics-service"`  reads independently.

## 4.4 Transactional Producer (Exactly-Once between topics)
For read-process-write pipelines:

```java
producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "billing-tx-1");
producerProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

KafkaProducer<String, String> producer = new KafkaProducer<>(producerProps);
producer.initTransactions();

consumerProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    if (records.isEmpty()) continue;

    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, String> r : records) {
            String invoice = createInvoice(r.value());
            producer.send(new ProducerRecord<>("invoices", r.key(), invoice));
        }
        // Atomically commit produced records + consumer offsets
        producer.sendOffsetsToTransaction(currentOffsets(consumer), consumer.groupMetadata());
        producer.commitTransaction();
    } catch (Exception e) {
        producer.abortTransaction();
    }
}
```
This gives **exactly-once semantics within Kafka** (across input topic → output topic → offset commit).

# Part 5: Event Sourcing
## 5.1 The Idea
In a traditional CRUD system, you **store the current state**:

```
account_balance: $500   ← overwrites the previous value
```
In **event sourcing**, you store the **sequence of events** that produced that state:

```
AccountOpened       balance=0
MoneyDeposited      amount=1000
MoneyWithdrawn      amount=300
MoneyWithdrawn      amount=200
```
**Current state = fold(events)** — you replay events to reconstruct it.

The event log is the **source of truth**, not the table.

## 5.2 Why Kafka Is Perfect for Event Sourcing
- Kafka is literally a **durable, ordered, replayable, append-only log** — the exact data structure event sourcing requires.
- **Partitioning by aggregate ID** (e.g., `accountId` ) gives per-aggregate ordering.
- **Log compaction** retains the latest snapshot per key forever.
- **Multiple consumers** can build different read models (projections) from the same event stream.
- **Replay** is built-in: `consumer.seek(0)`  rebuilds projections from scratch.
## 5.3 Concepts
- **Aggregate** — a consistency boundary (e.g., one bank account). All its events go to one partition (key = `accountId` ).
- **Event** — an immutable fact (`MoneyDeposited` ). Past tense.
- **Command** — a request to change state (`Deposit` ). May produce one or more events. May be rejected.
- **Projection / Read Model** — a denormalized view built by consuming events (e.g., a `current_balance`  table, an Elasticsearch index).
- **Snapshot** — a periodically saved state to avoid replaying from the beginning. Stored in a compacted topic or DB.
## 5.4 Architecture
```
Command          ┌─────────────────┐
(Deposit) ───────►│ Command Handler │
                  │  (Aggregate)    │
                  │  - load events  │
                  │  - apply rules  │
                  │  - emit events  │
                  └────────┬────────┘
                           │ append
                           ▼
                ┌──────────────────────┐
                │  Kafka topic         │
                │  "account-events"    │ ← single source of truth
                │  key = accountId     │
                └──────┬────────┬──────┘
                       │        │
            ┌──────────┘        └──────────┐
            ▼                              ▼
   ┌─────────────────┐           ┌──────────────────┐
   │ Balance         │           │ Audit/Reporting  │
   │ Projection      │           │ Projection       │
   │ (Postgres)      │           │ (Elasticsearch)  │
   └─────────────────┘           └──────────────────┘
```
**CQRS**: Commands write events → reads come from projections. Writes and reads are different models.

## 5.5 Java Example — Bank Account
### Events
```java
public sealed interface AccountEvent permits AccountOpened, MoneyDeposited, MoneyWithdrawn {
    String accountId();
}

public record AccountOpened(String accountId, String owner)         implements AccountEvent {}
public record MoneyDeposited(String accountId, long amountCents)    implements AccountEvent {}
public record MoneyWithdrawn(String accountId, long amountCents)    implements AccountEvent {}
```
### Aggregate (rebuilds state from events)
```java
public class Account {
    private String id;
    private String owner;
    private long balanceCents;
    private boolean exists;

    public void apply(AccountEvent e) {
        switch (e) {
            case AccountOpened o -> {
                this.id = o.accountId();
                this.owner = o.owner();
                this.balanceCents = 0;
                this.exists = true;
            }
            case MoneyDeposited d -> this.balanceCents += d.amountCents();
            case MoneyWithdrawn w -> this.balanceCents -= w.amountCents();
        }
    }

    // Command handler: validate and produce new events
    public List<AccountEvent> handleDeposit(long amountCents) {
        if (!exists) throw new IllegalStateException("Account does not exist");
        if (amountCents <= 0) throw new IllegalArgumentException("Amount must be > 0");
        return List.of(new MoneyDeposited(id, amountCents));
    }

    public List<AccountEvent> handleWithdraw(long amountCents) {
        if (!exists) throw new IllegalStateException("Account does not exist");
        if (amountCents > balanceCents) throw new IllegalStateException("Insufficient funds");
        return List.of(new MoneyWithdrawn(id, amountCents));
    }

    public long balanceCents() { return balanceCents; }
}
```
### Command handler — load, decide, append
```java
public class AccountService {
    private final KafkaProducer<String, AccountEvent> producer;
    private final EventStore eventStore;   // reads events for an aggregate

    public void deposit(String accountId, long amount) {
        // 1. Rebuild aggregate state by replaying its events
        Account account = new Account();
        for (AccountEvent e : eventStore.loadEvents(accountId)) {
            account.apply(e);
        }

        // 2. Validate and produce new events
        List<AccountEvent> newEvents = account.handleDeposit(amount);

        // 3. Append to Kafka (key = accountId guarantees per-account ordering)
        for (AccountEvent e : newEvents) {
            producer.send(new ProducerRecord<>("account-events", accountId, e));
        }
    }
}
```
### Projection — building a read model
```java
// Consumes "account-events" and maintains a Postgres "balances" table
public class BalanceProjection {
    private final JdbcTemplate jdbc;

    public void onEvent(AccountEvent e) {
        switch (e) {
            case AccountOpened o ->
                jdbc.update("INSERT INTO balances(id, owner, cents) VALUES (?,?,0) " +
                            "ON CONFLICT (id) DO NOTHING", o.accountId(), o.owner());
            case MoneyDeposited d ->
                jdbc.update("UPDATE balances SET cents = cents + ? WHERE id = ?",
                            d.amountCents(), d.accountId());
            case MoneyWithdrawn w ->
                jdbc.update("UPDATE balances SET cents = cents - ? WHERE id = ?",
                            w.amountCents(), w.accountId());
        }
    }
}
```
If the projection ever gets corrupted, just **drop the table, reset the consumer offset to 0, and replay** — Kafka still has every event.

### Snapshots (for performance)
For long-lived aggregates with thousands of events, periodically write a snapshot to a **compacted topic** keyed by aggregate ID:

```
account-snapshots (compacted, key = accountId)
"acc-123" → {balance: 5000, version: 1500}
```
To rebuild: load snapshot → apply events with `version > 1500`. Avoids replaying from event 0.

## 5.6 When to Use Event Sourcing — Practical Scenarios
### ✅ Strong fits
- **Banking, payments, accounting** — regulators require a full audit log; "current balance" is a derivation, not the truth.
- **Order management / e-commerce** — order lifecycle (placed → paid → shipped → delivered → returned) is naturally event-driven and auditable.
- **Insurance, claims processing** — every state change has legal significance.
- **Inventory & supply chain** — reconstructing what was in stock at any moment, supporting reversals.
- **IoT / sensor data** — events arrive as facts; you build projections (current temperature, hourly averages).
- **Collaborative systems** — Git, Google Docs, Figma all use event-sourcing-like models.
- **Compliance, audit, regulatory systems** — you need to prove **why** the state is what it is.
- **Systems where "time travel" matters** — "what did the customer see yesterday at 3 PM?"
- **Microservices integration** — events become the inter-service contract; each service builds its own projection.
### ❌ Poor fits
- **Simple CRUD apps** — overkill; just use a database.
- **Heavily transactional, read-heavy workloads with no audit needs** — added complexity isn't worth it.
- **Systems where requirements are still very volatile** — once you publish an event schema, evolving it is hard.
- **Small teams** — the operational burden (versioning events, replays, snapshots, projections) is real.
### Trade-offs
| Pros | Cons |
| ----- | ----- |
| Full audit log | Schema evolution is painful |
| Easy debugging ("what happened?") | Eventual consistency between command and read sides |
| Easy to add new projections later | Steeper learning curve |
| Time travel and replay | Need snapshots for performance |
| Natural fit for event-driven microservices | Storage grows unbounded (unless compacted) |
| Decoupled read models scale independently | More moving parts |
### Rule of thumb
>  Use event sourcing when **the history of changes is as important as the current state** — or more important. If you ever hear "we need to know why this changed," "we need a full audit," or "we need to reprocess past data with new logic," it's a strong signal.

# Part 6: Production Tips
- **Replication factor 3, **`**min.insync.replicas=2**` **, **`**acks=all**`  — standard durability.
- **Partition count** — set based on target throughput and max consumer parallelism. Hard to reduce later; start with reasonable headroom.
- **Always set timeouts and retries** on producers; enable idempotence.
- **Monitor consumer lag** — it's the #1 health signal.
- **Use schema registry** (Avro/Protobuf/JSON-Schema) — schemas evolve; you don't want surprises.
- **Plan retention deliberately** — time-based for streams, log compaction for state.
- **For event sourcing** — version events from day one (`v1` , `v2` ), use upcasters, never mutate published events.
- **Test rebalances and broker failures** — chaos-test your consumers.
---

# TL;DR
- Kafka is a **distributed append-only log** of records, partitioned for parallelism and replicated for durability. Performance comes from sequential I/O, page cache, zero-copy, and batching.
- **Producers** append by key (which determines partition). **Consumers** pull in batches, track offsets, and scale via consumer groups.
- **Event sourcing** stores all state changes as immutable events; current state is derived by replay. Kafka is an ideal event store: durable, ordered, replayable, partitioned.
- Use event sourcing when **history, auditability, and time-travel** matter — banking, orders, inventory, compliance, microservices integration. Avoid it for simple CRUD.
